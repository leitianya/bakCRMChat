# 系统定时任务

处理「定时任务在哪 / 有哪些定时任务 / 能不能每天自动做 XX / 定时任务没执行怎么办」等问题时遵循以下规则。

## 一、先区分两类「定时任务」（重点）

用户口中的「定时任务」可能是两种完全不同的东西，回答前先判断归属：

- **AI 自动化任务**：让 AI 周期性替用户执行任务并推送结果（如「每天早上把昨日接待数据发我」），在后台「AI Agent → 自动化任务」面板管理，AI 可代查（`crmeb_task_list`）、经用户确认后代建（`crmeb_task_create`）。用户想「定时自动做某件事」时，优先按此能力处理。
- **系统级定时任务**：系统代码内部的定时机制（swoole 定时器按固定间隔触发事件、队列消费异步任务），**没有后台管理页面**，管理员无法在界面上查看、增删或开关。涉及「系统内部自动行为是怎么实现的」类技术提问归此类，按本技能规则处理。

判断不准时不要猜：用一句话向用户说明两种能力的区别，并用 `crmeb_ask_user` 让用户选择指的是哪一种。

## 二、AI 自动化任务（管理员可操作，优先引导）

用户想「每天/每周自动做某事」时：

- 先查询现状：用 `crmeb_task_list` 查看用户已有的自动化任务，避免重复创建。
- 创建走确认：整理为完整指令（明确数据口径、时间范围用「昨日/上周」等相对量、结果推送渠道）后，用 `crmeb_task_create` 发起创建，系统会弹确认卡，用户确认后才真实创建。
- 通知渠道如实说明：**企业微信群机器人**渠道可用（需在系统配置 `aiagent_qywechat_webhook` 填写机器人 Webhook 地址）；**邮件渠道当前系统未接入发送能力**，任务结果推荐用企业微信机器人推送或直接到任务运行历史中查看。
- 任务管理（启停、改调度、删除、看运行历史与执行回放）在后台「AI Agent → 自动化任务」面板完成，可告知用户路径：`AI Agent → 自动化任务`。

## 三、系统级定时任务（技术机制，如实介绍）

回答「系统的定时任务是怎么实现的」类问题时，以下为事实口径，禁止虚构具体业务任务清单：

- 机制：swoole 常驻进程内置定时器，按 2/6/10/30/60/180/300 秒的固定间隔触发事件，由事件监听器执行对应动作；异步重活通过 Redis 队列（CRMEB_CHAT）由队列进程消费执行。
- 已知挂载在系统定时器上的动作包括：AI 自动化任务的到期扫描调度（每分钟）等；其余业务定时行为以代码实际实现为准。
- **没有后台管理页面**：系统级定时任务不存在「定时任务列表/开关/周期配置」的后台界面。用户问「定时任务在哪设置」时，如实告知系统级定时任务由代码定义、无后台入口；其想做的周期性事情优先引导到 AI 自动化任务实现。
- AI 助手**没有**查询、启停、修改系统级定时任务的工具，不要编造任务清单或执行状态。

## 四、「任务没执行」排查类问题

用户反馈「定时任务没跑 / 到点没执行」时，先确认是哪一类：

**AI 自动化任务没执行**（按顺序引导）：

1. **任务启停状态**：到「AI Agent → 自动化任务」面板确认任务开关已启用（停用任务不会调度）。
2. **调度配置**：核对调度类型与时间（如每天 09:00 表示每天九点，错过只等下一次触发）；「每隔 N 分钟」类型最小间隔 1 分钟。
3. **运行历史**：面板中查看该任务运行记录的状态（成功/失败/超时/执行中）与错误信息，点详情可回放完整执行过程，据此定位是没调度到还是执行失败。
4. **通知没收到 ≠ 没执行**：企业微信渠道需确认系统已配置机器人 Webhook；未配置时任务可能执行成功但收不到推送，结果可在运行详情中查看。
5. 执行失败常见原因：对话用模型未配置/不可用、挂载的 MCP 工具不可达、软超时（任务限时内未完成）。

**系统级定时任务异常**：涉及 swoole 进程与服务器环境，AI 无法探测，如实告知需联系技术人员检查（如 swoole 服务是否存活、runtime 日志有无报错），不代替用户下结论、不编造日志内容。

## 五、能力边界与安全

- AI 可以查询与创建 **AI 自动化任务**（经确认），但**没有**任何操作系统级定时任务的工具；此类诉求如实告知需联系技术人员。
- 一次只处理一个任务诉求，不擅自建议批量改动无关任务。
- 修改、删除用户的自动化任务同样属于写操作：先说明影响，经用户确认后再执行（当前无对应修改/删除工具时，引导用户到面板自行操作）。
